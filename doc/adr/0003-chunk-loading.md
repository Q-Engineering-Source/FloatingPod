# ADR-0003：区块加载、活动容量与传送

- 状态：已接受
- 日期：2026-08-06

## 背景

活动辅助机在玩家离线、死亡或远离时仍可能按终端最后指令待命或继续执行，因此需要保持所在区块加载。Forge 1.12.2 的 chunk ticket 有每票深度和每模组票数限制；若只依赖较低默认值，FloatingPod 可能在自身容量仍合法时被 Forge 意外拒绝。

同时，扩大 Forge 配额不能代替 FloatingPod 自己的性能门禁。实体、寻路、行为脚本和区块 tick 才是实际负载来源，必须由活动容量和每辅助机加载范围共同约束。

## 决策

1. 每个活动辅助机持有一个独立 Forge ticket，不把多个辅助机共享到同一 ticket，也不为一个辅助机拆分多个 ticket。
2. 默认 `radiusChunks=2`，加载以辅助机所在区块为中心的 5 x 5 方形，共 25 个区块。
3. config 可以扩大半径，但启动时必须校验 `(2 * radiusChunks + 1)^2 <= maximumChunksPerTicket`。不满足时快速失败并给出配置错误，不能截断加载范围后继续运行。
4. FloatingPod 在 `forgeChunkLoading.cfg` 中使用 `maximumChunksPerTicket=8192` 与 `maximumTicketCount=8192` 作为默认理论余量，避免 Forge 配额先于模组规则拒绝 ticket。
5. 全服活动辅助机上限由 FloatingPod config 管理，默认 256 且不得配置为超过 256。达到上限后拒绝新的释放请求；辅助机终端显示权威计数，例如 `16 / 256`。
6. 玩家注册槽位、玩家同时激活权益和全服活动上限分别校验。两类玩家升级是永久权益，不能绕过全服活动上限。
7. 服务端降低注册槽位时，不删除已注册辅助机，也不禁止这些既有辅助机按其他容量规则继续释放。降低同时激活上限时，不主动收回已经活动的超额辅助机；新的释放请求按新上限拒绝。管理员可用命令强制收回超额或非跟随状态的辅助机。
8. ticket 申请或移动更新失败时，立即停止对应辅助机行为并触发安全收回。必要状态持久化成功后才移除实体和释放已获得的区块；失败必须记录并暴露错误状态，不能静默强载、继续执行或声称收回成功。
9. Forge 强加载只承诺区块保持加载并 tick，不承诺模拟真实玩家的视距、watch 列表或客户端网络加载行为。
10. 同维度传送时，辅助机跟随玩家传送，并由服务端触发末影粒子和传送音效表现。
11. 玩家通过传送门跨维度时，辅助机也必须走对应传送门。若辅助机传送失败，则执行安全收回，待玩家到达目标位置后再于玩家身边释放；任何阶段都不能在两个位置或维度保留同一 UUID 的实体。
12. 释放、收回、管理员强制收回、ticket 失败和传送失败必须共用同一实体唯一性、活动计数和持久化合同，不能各自维护不一致的旁路逻辑。

## 影响

- `8192/8192` 不是可活动辅助机数量，也不是性能承诺。实际活动数量始终受不超过 256 的硬上限、玩家权益、实体成本和行为预算约束。
- 默认每台活动辅助机强加载 25 个区块；即使未达到 256 上限，服务器也可能先受实体、寻路或区块 tick 负载限制。管理员需要根据整合包负载调低活动上限或半径。
- 每辅助机独立 ticket 便于失败隔离和收回，但会增加 ticket 数量及移动时的更新成本，必须覆盖区块边界频繁移动测试。
- ticket 不可用时选择收回而不是降级运行，玩家可见行为会中断，但能避免在未加载世界中继续执行并丢失状态。
- 同维度传送和传送门路径需要服务端实体唯一性测试，并验证粒子与音效只作为表现事件，不能反向决定传送结果。

## 已否决方案

- **仅依赖 Forge 较低默认配额**：可能让 Forge 在 FloatingPod 自身容量合法时提前拒绝加载。
- **以 `8192/8192` 作为实际活动容量**：会绕过模组性能门禁；实际硬上限不超过 256。
- **ticket 失败后静默继续**：会导致行为运行在未加载或不完整世界中，禁止使用。
- **ticket 失败后丢弃实体状态**：会造成物品和所有权损失，禁止使用。
- **用多个 ticket 扩大单台辅助机范围**：当前范围必须装入单个 ticket，超出时启动校验失败。
- **把 Forge 强加载描述为完整玩家加载**：两者在视距、watch 和网络语义上不同，不作等价承诺。
