# 系统架构

## 架构原则

- **服务端权威**：世界状态、所有权、物品、模块、权益、行为结果和辅助机生命周期只由服务端决定。客户端只发送操作意图。
- **内存运行、数据库恢复**：节点健康运行期间，服务端内存中的领域状态是实时运行权威；所选数据库是崩溃恢复权威，并在 MySQL 跨服模式下承担节点协调事实来源。二者职责不同，不构成双写权威。
- **严格单节点写入**：任意时刻，一个辅助机 UUID 只能由一个逻辑节点持有活动写权限。跨服接管禁止 active-active。
- **关键变更同步提交**：可能影响所有权、物品安全、可执行代码版本或实体唯一性的变更，只有在数据库提交成功后才能向调用方报告成功。
- **定义与执行分离**：ZenScript 生成经过审批和校验的不可变行为定义；运行时只执行当前已发布的注册表快照。
- **能力由模块授予**：行为模块 `ItemStack` 是能力来源，配置界面只是安装、拆卸和调整入口。
- **显式失败**：数据库、Forge ticket、脚本校验或跨服接管失败必须保留可诊断状态并记录上下文，不能静默降级、复制实体或丢失状态。

## 运行组件与边界

### FloatingPod 服务端领域层

负责辅助机 UUID、所有权、预留与绑定、生命周期、玩家权益、活动容量、模块槽位、能量、耐久、护盾和行为状态。该层不依赖客户端渲染类，并通过接口访问持久化与外部能力。

### 行为运行时

把已安装模块解析为允许的行为集合，根据事件和调度条件执行行为，并实施每 tick 工作预算。行为运行时消费经过验证的不可变定义，不直接解释客户端输入或任意脚本源码。

### 脚本注册边界

负责接收服务端 ZenScript 声明，校验 ID、参数、依赖、冲突和权限，在全部校验成功后原子替换不可变注册表。失败保留旧快照，不以全局 `/ct reload` 作为 FloatingPod 发布入口。

### 公共持久化 Core

公共 Forge Core Mod 以普通 Scala/Java 接口和 JDBC 实现提供存储能力，不引入 Spring Boot。FloatingPod 只依赖存储合同，不把 SQLite 或 MySQL 细节扩散到领域对象。SQLite 与 MySQL 的模式选择、连接和 schema 迁移由服务端配置与存储实现负责。

### BungeeCord 中继

BungeeCord 插件只中继节点发现、玩家跨服和 handoff 消息，不拥有辅助机业务状态，也不能绕过数据库中的 authority、epoch、版本号和幂等校验。代理端口只属于连接元数据，不能作为持久节点身份。

### 客户端表现与网络协议

客户端负责配置 GUI、GeckoLib 模型、动画、粒子、音效和输入。客户端请求只表达意图，例如召回、释放、模块安装或配置变更；服务端重新验证玩家身份、所有权、容器会话、物品、权限、容量与参数，并向相关客户端同步必要快照或表现事件。

## 权威数据流

### 普通操作

1. 客户端发送带目标 UUID、预期状态版本和必要参数的操作意图。
2. 服务端验证发送者、所有权、权限、距离、容器会话、模块规则和状态版本。
3. 服务端在领域层计算变更，不接受客户端提供的最终状态。
4. 若属于关键变更，服务端同步提交数据库；提交失败则操作失败，内存不得发布未持久化的成功状态。
5. 若属于非关键高频状态，服务端更新内存、标记该辅助机为脏，并由其独立计时器批量持久化。
6. 服务端提交内存状态并向客户端同步最小状态快照或表现事件。

### 实时权威与恢复权威

- 服务端内存保存当前实体位置、导航目标、动画阶段和其他高频运行状态。进程异常退出时，这些非关键状态允许回退到最近一次成功刷盘，最长约为一个配置的持久化周期。
- 数据库保存可恢复快照和关键事务记录。服务端启动、节点接管或实体重建时只能从成功提交的数据恢复，不能从客户端 NBT、活动实体猜测所有权或版本。
- 每个辅助机使用独立的持久化计时，默认间隔为 30 秒，避免所有辅助机在同一 tick 集中刷盘。间隔可通过 config 调整。
- 辅助机或模块配置修改、绑定、转让、权益变更、模块安装或拆卸、物品变化、脚本版本变化、释放、召回和跨服接管属于关键变更，必须立即持久化。
- 正常停服必须停止接收新变更，等待进行中的关键事务结束，并对全部脏辅助机执行最终刷盘。

## 持久化模式

### 模式选择

`SQLite` 与 `MySQL` 是 config 中互斥的启动模式：

- **SQLite**：面向单人世界或独立单服，使用本节点数据库持久化，不提供跨服同步选项。
- **MySQL**：面向需要跨服同步的 BungeeCord 网络。参与节点必须连接同一个指定数据库，才可启用跨服 handoff。

两个模式禁止共存、双写和故障时自动互相降级。backend 类型、数据库地址、节点身份等设置只允许停服修改并在重启时校验。MySQL 正式兼容目标为 MySQL 8.x 与 InnoDB；TLS 与连接参数由服务端 config 提供。数据库密码不得进入客户端、辅助机 NBT、中继消息或日志。

SQLite 没有跨服镜像、跨服迁移或每服数据库间的复制协议。服务器即使处于同一个 BungeeCord 网络，SQLite 模式也不能自动在目标服恢复辅助机。

### 持久化内容

持久记录至少包含：

- 辅助机 UUID、schema 版本和状态版本。
- 当前所有者 UUID、所有权版本、`UNBOUND` 预留者与绑定状态。
- 生命周期状态、authority 逻辑节点 ID、服务器 UUID、epoch 和节点会话信息。
- 玩家注册权益、同时激活权益及辅助机当前活动状态。
- 模块 `ItemStack`、模块配置、允许持久化的行为状态和所引用的不可变脚本版本。
- 电量、耐久、护盾以及崩溃恢复所需的最近安全位置。
- 跨服 operation ID、handoff 阶段、目标节点、租约和幂等处理结果。

运行时不再使用“每辅助机一个 `.dat` 文件”。数据库是唯一恢复存储，迁移包只用于管理员显式导入和导出。

### 运行时导入与导出

管理员可以在服务器运行期间导出或导入单个辅助机迁移包。迁移包携带 UUID、schema、内容哈希、所有权及状态版本、模块 `ItemStack`、配置和脚本版本；不携带活动实体、Forge ticket、节点会话或数据库凭据。

导入流程先解析并完整校验，再通过所选 backend 原子提交。UUID 冲突默认拒绝，只有显式 replace 或迁移操作才允许覆盖。导入成功的辅助机保持收回状态，不自动生成实体。导入和导出不能切换 backend，也不能形成第二个运行时权威。

## MySQL 跨服接管

跨服能力只在 MySQL 模式、共享同一数据库且 BungeeCord 中继可用时启用。节点使用固定逻辑节点 ID 与服务器 UUID 标识；端口迁移、复用或代理映射不会改变节点身份。

每次 handoff 使用唯一 operation ID，并遵循 `PREPARE -> CLAIM -> ACK`：

1. 源服停止辅助机行为，安全收回实体，并将目标节点、operation ID、递增 epoch 与状态版本同步提交为 `PREPARED`。
2. BungeeCord 至少三次重试传递接管通知；重复、延迟或乱序消息必须由 operation ID、epoch 和状态版本幂等处理。
3. 目标服在数据库中以比较并交换方式确认 authority，提交 `CLAIM` 后才有资格生成实体。
4. 目标服成功接管并完成本地恢复后发送 `ACK`。源服收到重复 ACK 只更新同一操作的确认结果，不重新执行迁移。

准备租约默认 60 秒。超时、断线或 ACK 丢失时，源服必须保持辅助机已收回状态，不能自动重新激活；管理员通过 reconciliation 命令重试、取消或恢复。任何失败路径都不得让源服和目标服同时生成同一 UUID 的实体。

## 活动容量与区块加载

- 全服活动辅助机上限由 config 管理，默认 256，允许值不得超过 256。达到上限时拒绝新的释放请求；终端显示服务端权威计数，例如 `16 / 256`。
- 玩家注册槽位、玩家同时激活权益和全服活动上限分别校验，不能互相替代。
- 服务端降低注册槽位时，不删除已注册辅助机，也不禁止这些既有辅助机按其他容量规则继续释放。降低同时激活上限时，不自动收回已活动的超额辅助机；新的释放请求按新上限拒绝。管理员可显式强制收回超额或非跟随状态的辅助机。
- 每个活动辅助机使用一个独立 Forge ticket。默认 `radiusChunks=2`，加载以辅助机所在区块为中心的 5 x 5 方形，共 25 个区块。
- config 可以扩大半径，但启动时必须校验 `(2 * radiusChunks + 1)^2 <= maximumChunksPerTicket`。当前不使用多个 ticket 拆分单个辅助机的加载范围。
- FloatingPod 在 `forgeChunkLoading.cfg` 中的默认余量为 `maximumChunksPerTicket=8192`、`maximumTicketCount=8192`。这只是避免 Forge 过早拒绝本模组 ticket 的理论上限，不扩大 256 个活动辅助机硬上限。
- ticket 申请或更新失败时，服务端停止该辅助机行为并触发安全收回。必要状态提交成功后才能移除实体和释放已获得的区块；持久化失败时保留显式错误状态并记录日志，不能伪装成已收回。
- Forge 强加载保证目标区块持续加载并 tick，不承诺完整模拟真实玩家的视距、watch 列表或网络加载语义。

## 释放、收回与传送

释放是一次服务端事务边界：先校验所有权、玩家权益、全服活动容量、模块状态、生成位置和 Forge ticket，再持久化释放状态并创建唯一实体。任一步骤失败都不能留下活动计数、ticket 或重复实体。

收回先停止行为和新的状态变更，提交必要状态，再移除实体、释放 ticket 并更新活动计数。ticket 失败、管理员命令、跨服 handoff 和玩家终端操作都复用同一收回合同。

同维度传送时，活动辅助机跟随玩家传送，并由客户端按服务端事件播放末影粒子和传送音效。通过传送门跨维度时，辅助机也必须走对应传送门；若辅助机传送失败，服务端将其收回，并在玩家到达目标位置后于玩家身边重新释放。任何传送失败都不得在两个位置或两个维度保留同一辅助机实体。

## 实施验证重点

- 验证 Cleanroom 1.12.2 下 Forge ticket 的申请、恢复、移动和释放回调顺序，确保实体与 ticket 生命周期一致。
- 对进程崩溃点做故障注入，覆盖关键数据库提交前后、实体生成前后和 handoff 各阶段，证明不会复制物品、所有权或实体。
- 对 MySQL 断线、超时、重复消息、旧 epoch、节点重启和租约过期执行集成测试。
- 对 30 秒独立计时器进行负载与抖动测试，证明不会形成集中刷盘尖峰，并验证非关键状态最多只回退一个成功持久化周期。
- 对运行时导入、冲突拒绝、显式替换和 schema 不兼容执行事务测试，确保失败不改变既有记录。
