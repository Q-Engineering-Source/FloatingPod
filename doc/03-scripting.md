# ZenScript 脚本系统

## 目标与信任边界

ZenScript 用于声明 FloatingPod 的行为定义、行为模块和可调参数。脚本只在服务端加载，客户端不能上传、编译或执行脚本，也不能把脚本执行结果作为权威状态提交。

服务器管理员可以直接管理脚本。获得授权的玩家只能提交源码；提交内容必须经过管理员审批，才能生成可安装的数据盘。审批意味着管理员接受该版本在受控 FloatingPod API 内执行，不意味着 ZenUtils 或 CraftTweaker 提供了通用的不可信代码沙箱。

服务端 config 提供玩家自定义行为总开关。关闭时，玩家只能调整管理员预制脚本已经声明并允许修改的配置项，不能提交脚本或从空数据盘生成玩家脚本。开启时，提交、审批和数据盘生成仍分别执行权限校验，不能因开关开启而默认授权全部玩家。

FloatingPod 对玩家脚本只公开自己的领域 API。文件、网络、线程、反射、任意类加载以及通用 CraftTweaker 配方和事件入口均不属于允许边界。`fastScriptLoading` 与 `crossLoaderAccess` 必须关闭，避免绕过加载事件或跨 loader 访问。

## 声明模型

脚本注册表围绕稳定 ID 建立，并至少支持以下定义：

- **行为定义**：唯一 ID、触发条件、执行动作、冷却、优先级和资源成本。
- **行为模块定义**：对应物品、提供的行为、类别、槽位成本、冲突项和依赖项。
- **参数定义**：类型、范围、默认值、是否允许运行时修改以及显示信息键。
- **策略定义**：目标筛选、移动模式以及后续战斗、采集和存储模块可复用的规则。

首个公开用例是“跟随策略数据盘”，其参数为跟随距离、相对方位和移动模式。具体类名和 ZenScript 语法在工具链探针通过后单独设计，不能由本文中的概念名称隐含推导。

## 提交、审批与版本

1. 获授权玩家向服务端提交严格 UTF-8 源码。
2. 服务端保存原始内容，计算精确内容哈希，并创建不可变候选版本。
3. 管理员终端显示提交者、内容哈希、版本和校验诊断。
4. 管理员发起检查后，服务端对该候选执行解析、类型检查和 FloatingPod 领域约束检查。
5. 任一错误都会拒绝审批；失败候选不能修改当前活动注册表。
6. 审批成功后发布该精确哈希和不可变版本，获授权玩家可用空数据盘生成对应脚本数据盘。
7. 源码任何变化都会产生新哈希和新版本，必须重新审批。

撤销针对精确版本立即生效。已经存在的数据盘保留物品和配置，但显示“已撤销”，且服务端拒绝继续执行该版本。数据盘只保存稳定脚本 ID、不可变版本和自身配置，不序列化可执行对象。

## 语义检查

审批检查包括：

- ZenScript 解析与类型检查。
- loader、preprocessor 和 API 命名空间准入。
- 重复 ID、无效引用、依赖环、冲突、槽位成本和参数范围。
- 行为动作、资源成本和可持久化字段是否属于 FloatingPod 允许集合。
- 候选事务执行期间记录的任意业务异常。

语义检查不试运行任意世界副作用，也不能仅以 ZenUtils 的 `ScriptReloadEvent.Post` 或 loader 状态判定成功。CraftTweaker 错误记录、实际 loader 阶段和 FloatingPod 自己的事务状态都必须检查。

## 原子发布

FloatingPod 使用专用 loader 和自己的发布命令，不使用全局 `/ct reload` 作为发布入口。

1. 所有候选注册 action 只写入独立的可变 builder，不修改活动注册表。
2. 审批和发布在服务端主线程串行执行，避免竞争 CraftTweaker 全局状态。
3. 只有目标 loader 完成、状态成功、错误记录为空且 FloatingPod 事务有效时，才能构造不可变候选快照。
4. 服务端通过单次原子替换发布不可变快照。
5. 任意失败都丢弃候选并保留旧快照，同时记录首个错误、脚本来源、内容哈希和版本。

该流程只替换 FloatingPod 行为注册表，不承诺为其他 CraftTweaker 或 ZenUtils 状态提供事务回滚。

## 运行时执行

- 服务端根据已安装模块和已发布脚本版本创建行为实例。
- 客户端提交的配置值必须按当前定义的类型、范围、权限和版本重新验证。
- 每个辅助机和玩家都受服务端行为预算约束；脚本不能创建无界循环、无界任务或绕过全服活动上限。
- 单个行为异常必须携带辅助机 UUID、所有者、行为 ID、脚本哈希和触发上下文写入日志，并停止对应行为实例，不能终止服务端进程。
- 注册表撤销或替换后，旧行为实例在下一个安全调度边界停止；服务端不能继续执行已撤销版本。

## 权限来源

LuckPerms 存在时是玩家提交、审批管理和数据盘生成权限的事实来源。FloatingPod 内置权限后端用于没有 LuckPerms 的环境，并始终保存审批流程状态。多个来源冲突时，任何明确拒绝优先于允许。

管理员审批权限、玩家提交权限、已批准版本的数据盘生成权限和脚本运行权限分别校验，不能用其中一个权限隐式授予其他能力。

## 验收重点

1. 解析、类型或领域约束失败时，活动注册表保持字节等价的旧快照。
2. 同一内容哈希重复提交和发布具有幂等结果，不产生多个可变版本。
3. 修改、撤销、旧数据盘执行和无权限生成均被服务端正确拒绝。
4. 客户端伪造脚本 ID、版本或配置不能绕过审批和模块安装规则。
5. 脚本 action 抛出异常时事务标记失败，即使底层 loader 状态仍显示成功也不能发布。
6. 专用服务端重启后，已批准版本和撤销状态从数据库恢复，且不会自动执行未发布候选。
